# Understanding `config.toml`

The project uses TOML files to configure the AI agent. Configuration controls:

- Which model is used
- How many turns and prompt tokens are allowed
- Which operations require approval
- Which tools are available
- Shell environment behavior
- Lifecycle hooks
- MCP servers
- Instructions given to the model
- Debug mode

The main configuration model is [`Config`](<d:/Gen AI/CLI agent.worktrees/ai-coding-agent-main/config/config.py>).
The configuration is loaded by [`load_config()`](<d:/Gen AI/CLI agent.worktrees/ai-coding-agent-main/config/loader.py>).

The general structure is:

```text
config.toml
  |
  +-- top-level agent settings
  +-- [model]
  +-- [shell_environment]
  +-- [[hooks]]
  +-- [mcp_servers.<name>]
```

## 1. Where configuration files are read from

The loader checks two TOML locations:

### User/system configuration

The platform-specific user configuration directory contains:

```text
<user config directory>/cli-agent/config.toml
```

The path is generated by `platformdirs.user_config_dir("cli-agent")`.

### Project configuration

The current working directory may contain:

```text
<project>/.cli-agent/config.toml
```

The project configuration is loaded after the user/system configuration and overrides
matching values.

Example:

```text
User config:
  model.temperature = 0.7

Project config:
  model.temperature = 0.1

Effective value:
  model.temperature = 0.1
```

Nested dictionaries are merged recursively. Unrelated settings from the user
configuration remain available.

## 2. Working directory selection

The CLI can receive a working directory:

```bash
python main.py --cwd C:/projects/demo
```

If the TOML files do not define `cwd`, the loader inserts the CLI directory:

```python
config_dict["cwd"] = cwd
```

The configuration field itself is:

```python
cwd: Path = Field(default_factory=Path.cwd)
```

TOML example:

```toml
cwd = "C:/projects/demo"
```

This directory is used by tools, discovery, hooks, MCP stdio servers, and the terminal
UI.

# Top-level parameters

## 3. `hooks_enabled`

Type:

```toml
hooks_enabled = true
```

Python type:

```python
bool
```

Default:

```text
false
```

When enabled, configured lifecycle hooks can run before or after agent and tool
operations.

Example:

```toml
hooks_enabled = true
```

Setting this to `false` disables the hook system globally even if `[[hooks]]` entries
exist.

See [`HOOKS.md`](<d:/Gen AI/CLI agent.worktrees/ai-coding-agent-main/HOOKS.md>) for
the hook lifecycle and script examples.

## 4. `max_turns`

Type:

```toml
max_turns = 20
```

Python type:

```python
int
```

Validation:

```text
minimum: 1
maximum: 1000
```

This limits the number of agent turns in a run.

Example:

```toml
max_turns = 50
```

Use a smaller value for testing:

```toml
max_turns = 5
```

## 5. `max_prompt_tokens`

Type:

```toml
max_prompt_tokens = 50000
```

Python type:

```python
int
```

Validation:

```text
minimum: 1
```

This is the maximum prompt-token budget checked by the agent before continuing. It is
separate from the model's `context_window`.

Example:

```toml
max_prompt_tokens = 50000
```

The interactive `/config` command displays this value.

## 6. `cwd`

Type:

```toml
cwd = "C:/projects/demo"
```

Python type:

```python
Path
```

The path becomes the agent's working directory. Relative tool paths are resolved
against it:

```text
cwd: C:\projects\demo
tool path: src/main.py
resolved path: C:\projects\demo\src\main.py
```

Usually, passing `--cwd` is preferable because it makes the selected project explicit:

```bash
python main.py --cwd C:/projects/demo
```

## 7. `approval`

Type:

```toml
approval = "on-request"
```

The accepted enum values are:

| Value          | Meaning                                                |
| -------------- | ------------------------------------------------------ |
| `"on-request"` | Ask when a tool requests confirmation                  |
| `"on-failure"` | Use approval behavior associated with failures         |
| `"auto"`       | Automatically approve according to the approval system |
| `"auto-edut"`  | Current enum spelling for the `AUTO_EDIT` member       |
| `"never"`      | Never approve through the normal approval flow         |
| `"yolo"`       | Fully permissive mode                                  |

Example:

```toml
approval = "on-request"
```

The default is:

```text
on-request
```

The value can also be changed at runtime:

```text
/approval auto
```

## 8. `allowed_tools`

Type:

```toml
allowed_tools = ["read_file", "grep", "glob"]
```

Python type:

```python
list[str] | None
```

If omitted or set to `null`, all registered tools are available subject to the rest of
the tool system.

If provided, only names in the list are exposed:

```toml
allowed_tools = [
  "read_file",
  "grep",
  "glob",
  "list_dir"
]
```

This is useful for a read-only investigation agent:

```toml
allowed_tools = ["read_file", "grep", "glob", "list_dir"]
```

Tool names must match registered names. MCP tools include their server prefix, for
example:

```toml
allowed_tools = [
  "read_file",
  "filesystem__read_file"
]
```

## 9. `developer_instructions`

Type:

```toml
developer_instructions = """
Follow the repository coding conventions.
Run targeted tests after code changes.
"""
```

Python type:

```python
str | None
```

These instructions are included in the developer-instructions section of the system
prompt.

Multiline TOML strings are useful:

```toml
developer_instructions = """
- Prefer small, focused changes.
- Do not modify generated files.
- Explain important implementation decisions.
"""
```

If this key is not present, the loader attempts to read `AGENTS.MD` from the working
directory and uses its contents as developer instructions.

## 10. `user_instructions`

Type:

```toml
user_instructions = """
Keep explanations concise and include examples.
"""
```

Python type:

```python
str | None
```

These instructions are included in the user-instructions section of the system prompt.
They are different from a message typed during the conversation: they are persistent
configuration-level guidance.

## 11. `debug`

Type:

```toml
debug = true
```

Python type:

```python
bool
```

Default:

```text
false
```

This flag is available on `Config` for debugging behavior. Set it explicitly when
debugging:

```toml
debug = true
```

# `[model]`

## 12. `model.name`

The nested model table configures the language model:

```toml
[model]
name = "gpt-4o"
```

Python type:

```python
str
```

If `name` is omitted, the model name defaults from the `MODEL_NAME` environment
variable:

```text
MODEL_NAME=gpt-4o
```

Example:

```toml
[model]
name = "gpt-4o-mini"
```

The CLI displays it in the welcome panel and `/config` output. It is also used when
selecting tokenization and creating the LLM client.

## 13. `model.temperature`

Type:

```toml
[model]
temperature = 0.2
```

Python type:

```python
float
```

Validation:

```text
minimum: 0.0
maximum: 2.0
```

Lower values usually make responses more deterministic:

```toml
temperature = 0
```

Higher values allow more variation:

```toml
temperature = 1.0
```

The default is `1`.

## 14. `model.context_window`

Type:

```toml
[model]
context_window = 256000
```

Python type:

```python
int
```

This describes the model's context capacity and is used by context management and
compaction decisions.

Example:

```toml
[model]
name = "gpt-4o"
temperature = 0.2
context_window = 128000
```

# `[shell_environment]`

The shell policy controls which environment variables are passed to shell commands.

## 15. `shell_environment.ignore_default_excludes`

Type:

```toml
[shell_environment]
ignore_default_excludes = false
```

Python type:

```python
bool
```

Default:

```text
false
```

When false, the shell tool excludes variables matching the default patterns:

```text
*KEY*
*TOKEN*
*SECRET*
```

This helps avoid exposing credentials to subprocesses.

## 16. `shell_environment.exclude_patterns`

Type:

```toml
[shell_environment]
exclude_patterns = ["*KEY*", "*TOKEN*", "*SECRET*", "*PASSWORD*"]
```

Python type:

```python
list[str]
```

These patterns are matched against environment variable names.

Example:

```toml
[shell_environment]
exclude_patterns = [
  "*KEY*",
  "*TOKEN*",
  "*SECRET*",
  "*PASSWORD*",
  "AWS_*"
]
```

The list replaces the default list when explicitly supplied.

## 17. `shell_environment.set_vars`

Type:

```toml
[shell_environment.set_vars]
APP_ENV = "development"
LOG_LEVEL = "debug"
```

Python type:

```python
dict[str, str]
```

These values are added to the environment used by shell commands:

```toml
[shell_environment.set_vars]
APP_ENV = "test"
PYTHONUNBUFFERED = "1"
```

Do not store secrets directly in a project configuration file. Prefer environment
variables or a secret manager.

## 18. Complete shell example

```toml
[shell_environment]
ignore_default_excludes = false
exclude_patterns = ["*KEY*", "*TOKEN*", "*SECRET*", "*PASSWORD*"]

[shell_environment.set_vars]
APP_ENV = "development"
PYTHONUNBUFFERED = "1"
```

The shell tool starts from the current environment, removes excluded variables unless
the default exclusions are disabled, and applies `set_vars`.

# `[[hooks]]`

Hooks are repeated TOML tables. Each table describes one lifecycle hook.

## 19. Hook parameters

```toml
[[hooks]]
name = "test_before_tool"
trigger = "before_tool"
command = "python ./scripts/test_tool.py"
timeout_sec = 30
enabled = true
```

Fields:

| Field         | Type   | Required | Meaning                                     |
| ------------- | ------ | -------: | ------------------------------------------- |
| `name`        | string |      yes | Human-readable hook name                    |
| `trigger`     | string |      yes | Lifecycle event                             |
| `command`     | string |     no\* | Command to execute                          |
| `script`      | string |     no\* | Script content or script configuration      |
| `timeout_sec` | float  |       no | Maximum execution time; default `30`        |
| `enabled`     | bool   |       no | Whether this hook is active; default `true` |

\* At least one of `command` or `script` must be provided.

## 20. Hook triggers

Accepted trigger values:

| Trigger          | Runs                                |
| ---------------- | ----------------------------------- |
| `"before_agent"` | Before an agent run                 |
| `"after_agent"`  | After an agent run                  |
| `"before_tool"`  | Before a tool call                  |
| `"after_tool"`   | After a tool call                   |
| `"on_error"`     | For configured error handling paths |

Example:

```toml
[[hooks]]
name = "before_agent_check"
trigger = "before_agent"
command = "python scripts/check_environment.py"
timeout_sec = 10
enabled = true
```

## 21. Command hooks

A command hook runs an external command:

```toml
[[hooks]]
name = "after_tool_log"
trigger = "after_tool"
command = "python scripts/log_tool.py"
timeout_sec = 20
enabled = true
```

The command is executed using the configured working directory and hook environment.

Use paths that work on the target operating system. For a Windows project:

```toml
command = "python scripts\\check.py"
```

or use a path form supported by the shell:

```toml
command = "python scripts/check.py"
```

## 22. Script hooks

The configuration model also accepts `script`:

```toml
[[hooks]]
name = "before_tool_script"
trigger = "before_tool"
script = """
echo "Tool is about to run"
"""
timeout_sec = 10
```

The hook system determines how the configured script is executed. Use `command` when
you want to invoke a named script file or interpreter explicitly.

## 23. Multiple hooks

Add one `[[hooks]]` block per hook:

```toml
hooks_enabled = true

[[hooks]]
name = "before_agent_check"
trigger = "before_agent"
command = "python scripts/check.py"

[[hooks]]
name = "before_tool_check"
trigger = "before_tool"
command = "python scripts/test_tool.py"

[[hooks]]
name = "after_tool_log"
trigger = "after_tool"
command = "python scripts/log_tool.py"
enabled = false
```

The `enabled = false` hook remains configured but is skipped.

# `[mcp_servers.<name>]`

Each named table configures one Model Context Protocol server.

## 24. Common MCP parameters

```toml
[mcp_servers.filesystem]
enabled = true
startup_timeout_sec = 10
```

| Field                 | Type             | Default | Meaning                              |
| --------------------- | ---------------- | ------: | ------------------------------------ |
| `enabled`             | bool             |  `true` | Whether to start this server         |
| `startup_timeout_sec` | float            |    `10` | Connection timeout                   |
| `command`             | string           |    none | Local stdio server command           |
| `args`                | array of strings |    `[]` | Arguments for the command            |
| `env`                 | table            |    `{}` | Environment overrides for the server |
| `cwd`                 | path             |    none | Server subprocess working directory  |
| `url`                 | string           |    none | HTTP/SSE server endpoint             |

Every server must provide exactly one of:

```text
command
url
```

It is invalid to provide neither or both.

## 25. Stdio MCP server

```toml
[mcp_servers.filesystem]
enabled = true
startup_timeout_sec = 10
command = "npx"
args = [
  "-y",
  "@modelcontextprotocol/server-filesystem",
  "C:/projects/demo"
]
```

This starts a local process and communicates through standard input/output.

## 26. Stdio environment and working directory

```toml
[mcp_servers.database]
enabled = true
command = "python"
args = ["servers/database_server.py"]
cwd = "C:/projects/demo"

[mcp_servers.database.env]
DATABASE_URL = "sqlite:///C:/projects/demo/data.db"
APP_ENV = "development"
```

The server receives the configured environment overrides. Avoid committing passwords,
tokens, or private connection strings.

## 27. HTTP/SSE MCP server

```toml
[mcp_servers.remote_tools]
enabled = true
startup_timeout_sec = 15
url = "http://localhost:8000/sse"
```

The client uses the URL to create an SSE transport.

Invalid:

```toml
[mcp_servers.invalid]
command = "python server.py"
url = "http://localhost:8000/sse"
```

The model validator rejects a server containing both transport types.

## 28. Named MCP tools

If a server called `filesystem` exposes `read_file`, the local tool name becomes:

```text
filesystem__read_file
```

This name can be used in `allowed_tools`:

```toml
allowed_tools = [
  "read_file",
  "filesystem__read_file"
]
```

See [`TOOLS_MCP.md`](<d:/Gen AI/CLI agent.worktrees/ai-coding-agent-main/TOOLS_MCP.md>)
for the complete MCP lifecycle.

## 30. Important TOML syntax

### Scalar values

```toml
debug = false
max_turns = 20
temperature = 0.5
```

Model settings belong in the nested model table:

```toml
[model]
name = "gpt-4o"
temperature = 0.5
```

### Arrays

```toml
allowed_tools = ["read_file", "grep"]
args = ["-y", "package-name"]
```

### Tables

```toml
[model]
temperature = 0.5
```

### Repeated tables

```toml
[[hooks]]
name = "one"
trigger = "before_agent"
command = "python one.py"

[[hooks]]
name = "two"
trigger = "after_agent"
command = "python two.py"
```

### Named tables

```toml
[mcp_servers.first]
command = "python"
args = ["first_server.py"]

[mcp_servers.second]
url = "http://localhost:8000/sse"
```

## 31. Environment variables versus TOML

Some values are intentionally read from the environment rather than TOML:

| Environment variable | Used for                                                    |
| -------------------- | ----------------------------------------------------------- |
| `API_KEY`            | Application configuration validation and client credentials |
| `BASE_URL`           | Configured API base URL property                            |
| `MODEL_NAME`         | Default model name when `[model].name` is omitted           |

Example PowerShell setup:

```powershell
$env:API_KEY = "your-api-key"
$env:MODEL_NAME = "gpt-4o"
python main.py
```

Do not commit real credentials to `config.toml`.

## 32. Validation behavior

Pydantic validates the TOML after the user and project dictionaries are merged.

Examples of invalid values:

```toml
max_turns = 0
```

```toml
[model]
temperature = 3.0
```

```toml
[mcp_servers.bad]
```

An MCP server must have `command` or `url`.

```toml
[hooks]
name = "wrong-shape"
```

Hooks must be declared with `[[hooks]]`, because `hooks` is a list.

If validation fails, the loader raises `ConfigError`.

## 33. Configuration loading example

Suppose the user configuration contains:

```toml
[model]
name = "gpt-4o"
temperature = 0.7

max_turns = 100
```

The project `.cli-agent/config.toml` contains:

```toml
[model]
temperature = 0.1

max_turns = 20
```

The effective configuration is:

```text
model.name        = gpt-4o
model.temperature  = 0.1
max_turns          = 20
```

The project file overrides only the values it defines.

## 34. Config flow through the application

```text
main.py
  |
  v
load_config(cwd)
  |
  +-- read user config.toml
  +-- read project .cli-agent/config.toml
  +-- merge dictionaries
  +-- add cwd if missing
  +-- add AGENTS.MD instructions if needed
  +-- validate Config with Pydantic
  |
  v
CLI
  |
  +-- Agent
  +-- Session
  +-- ToolRegistry
  +-- Hooks
  +-- MCPManager
  +-- ContextManager
```

The same `Config` object is passed through the runtime so these components use one
consistent configuration.

## 35. Current implementation notes

1. The checked-in example
   [`.cli-agent/config.toml`](<d:/Gen AI/CLI agent.worktrees/ai-coding-agent-main/.cli-agent/config.toml>)
   uses Unix paths such as `/Users/...` and `/tmp`; update them for Windows or the
   target operating system before running the example.

2. The example defines `filesystem2` with the package name
   `@modelcontextprotocol/server-filesystem222222222222`, which appears intentionally
   invalid and may fail to start.

3. The `ApprovalPolicy.AUTO_EDIT` enum currently has the value `"auto-edut"` rather
   than `"auto-edit"`. Use the actual value if configuring it directly.

4. `Config.temperature` has a setter decorated with `@model_name.setter` in the current
   source. Reading `temperature` works, but assigning it through that property may not
   behave as intended. Configure it under `[model]` instead.

5. The loader catches invalid system or project TOML and logs a warning before
   continuing. A later validation error may therefore come from missing or incomplete
   settings rather than directly from the original parse failure.

6. The loader looks for `AGENTS.MD` when `developer_instructions` is absent. If the
   project uses a differently named instruction file, it will not be loaded
   automatically.

7. `API_KEY`, `BASE_URL`, and `MODEL_NAME` are environment-backed values; putting them
   at arbitrary top-level TOML keys does not set the properties exposed by `Config`.

## Summary

`config.toml` is the declarative control panel for the agent:

```text
Top-level settings
  -> runtime limits, approval, tools, instructions

[model]
  -> model name, temperature, context window

[shell_environment]
  -> shell variable filtering and overrides

[[hooks]]
  -> lifecycle commands and scripts

[mcp_servers.<name>]
  -> external MCP server connections
```

In short:

> Put stable project behavior in `.cli-agent/config.toml`, keep credentials in
> environment variables, and use the nested TOML tables to configure models, shell
> execution, hooks, and MCP servers.
